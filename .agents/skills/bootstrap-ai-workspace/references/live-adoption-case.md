# Dirty live-workspace adoption case

This anonymized case captures constraints validated in a large, dirty, actively operated workspace. It is a reusable safety example, not a status claim about any current project.

## Initial conditions

- Many modified and untracked paths already existed.
- Existing instructions, README material, and append-only status history carried business rules and active context.
- Large data, profile, virtual-environment, cache, secret-location, and nested-repository areas existed.
- Existing knowledge and AI evidence surfaces could not be replaced.
- Scripts still referenced historical paths, so visual neatness was not proof that moves were safe.

## Safe response

1. Inspect read-only and surface dirty state, sensitive-looking areas, nested repositories, large runtime zones, and governance gaps.
2. Preserve the native business layer in the catalog instead of forcing generic names.
3. Protect credential-bearing and runtime paths without reading or copying their values.
4. Add missing governance and owned managed blocks without replacing domain instructions or status history.
5. Make no business moves, deletion, permission changes, commits, hook installation, deployment, or external scheduler edits in the adoption pass.
6. Register genuine legacy gaps as precise debt instead of rewriting active business code to fit a generic shape.

## Validated iteration

The first real plan modified only owned blocks in three existing files and created missing control-plane files. Its first audit exposed legacy broken links in a mirrored package and an old research attachment. The receipt restored the existing files byte-for-byte before a refined plan excluded only those exact legacy surfaces.

A later review found a non-portable test fixture that would have copied an entire multi-gigabyte target. It was replaced with a generated minimal workspace. The reusable lessons are:

- preserve failed audits and use them to narrow the contract;
- prefer receipt rollback and clean replay over unreceipted patching;
- test template behavior against targets whose size and dirtiness differ materially from the template.
